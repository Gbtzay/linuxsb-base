# 看过的帖子返回首页路由隔离设计

## 状态

已获用户确认，进入实现前的规格记录阶段。

## 问题与目标

用户从首页软跳打开帖子、阅读后返回首页时，首页偶发出现帖子正文或评论楼层。首页已有同文档缓存，帖子路由不应进入该缓存；同时，帖子页实时流的迟到响应也不能在路由切换后写入当前首页出口。

成功标准：

- 从首页进入帖子，再通过壳内返回或浏览器后退恢复首页后，正文出口不包含 `.post-content-title`、`ul.topic-post-list` 或 `li.post-entry`。
- 延迟的帖子实时流响应在返回首页后不能被暂存内容消费到首页。
- 首页缓存仍可命中，返回首页不因本修复强制重新请求。
- 列表实时流和帖子实时流现有行为不变。

## 已确认的边界

`plugins/skin.user.js` 的 `stashView()` 已跳过帖子路由，首页缓存只在离开列表页时建立。因此本次不采用“禁止首页缓存”的症状修补，也不改变帖子正文不进入活跃 DOM 缓存的策略。

`plugins/live-feed.user.js` 已在部分网络响应完成点检查 `navGen` 和节点身份，但 `msgDelta()` 等异步等待之后以及最终插入函数没有统一复核当前路由、模式和出口节点。实时流状态包含全局 `ctx` 与 `pending`，这使迟到的帖子楼层有机会跨越路由边界。

## 设计

### 1. 回归测试

在 `test/skin.test.js` 增加一个皮肤与实时流集成测试，使用现有的 `makeTopicSpaHome()` 和 `deferredHtmlFetch()`：

1. 建立首页和首页缓存。
2. 进入帖子页。
3. 让帖子实时流请求保持未完成，并安排它返回带有新的 `post-entry` 的帖子 HTML。
4. 返回首页并等待缓存正文恢复。
5. 释放迟到响应，并触发一次实时流刷新/消费机会。
6. 断言首页正文只保留首页列表，不出现帖子标题、帖子楼层列表或 `post-entry`。

测试必须先在当前实现上失败，证明它捕获的是本次竞态而不是已有行为。

### 2. 实时流上下文守卫

在 `plugins/live-feed.user.js` 内部把当前写入上下文视为一组不可复用的身份：

- 导航代数 `navGen`；
- 当前模式（`list` 或 `topic`）；
- 当前出口节点 `ctx.ul`；
- 当前页面类型与帖子 ID（帖子模式）。

在以下位置使用同一套有效性判断：

- `msgDelta()` 等异步等待返回后继续显示横幅或消费 `pending` 前；
- `insertPending()` 写入列表前；
- `insertFloors()` 写入帖子楼层前；
- 事件驱动的 `tryFlush()` / 调试入口加载前，如它们可能使用跨异步边界留下的 `pending`。

有效性判断至少要求：

- 代数仍等于开始处理时的代数；
- 模式仍匹配；
- 出口节点仍连接在当前文档中；
- 当前选择器解析出的出口节点仍是同一个节点；
- 帖子模式的当前路由 ID 仍等于 `ctx.tid`；列表模式仍处于列表页。

判断失败时丢弃该轮对当前出口的写入。`pending` 必须随上下文代数归属：路由初始化时清理旧代数暂存；旧异步任务在恢复后不得覆盖或清理新代数已经产生的暂存内容，也不得改写新路由的横幅或 DOM。

### 3. 缓存策略

只有回归测试证明响应片段本身写入了首页缓存，才增加首页响应的路由身份校验。首选实现不改变 `stashView()`、`takeView()` 和首页缓存命中流程，避免把正常的快速返回改成额外网络请求。

## 非目标

- 不重构首页缓存系统。
- 不修改站点原生帖子路由或实时流接口。
- 不修复与本问题无关的淘帖详情测试失败。
- 不改变实时流的选主、轮询间隔、排序和提醒文案。
